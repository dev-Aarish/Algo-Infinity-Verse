01

Data Types & State Variables

Solidity is a statically typed language — every variable must declare its type at compile time. State variables are stored permanently on the blockchain (in contract storage), making them the backbone of any smart contract.

Value Types

  • bool — true or false
  • uint / uint256 — unsigned integer (256-bit, default for gas efficiency)
  • int / int256 — signed integer
  • address — 20-byte Ethereum address (0x...)
  • bytes32 — fixed-size byte array (32 bytes)
  • string — dynamically-sized UTF-8 string

State variables are declared at the contract level and written directly to the blockchain. Their visibility (public, private, internal) controls how they can be read.

Solidity 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract DataTypes {
    // ── State Variables ──
    bool public isActive = true;
    uint256 public counter = 42;
    int256 public temperature = -5;
    address public owner = 0x1234...;
    string public name = "Solidity";
    bytes32 public hash;

    // ── Enum ──
    enum Status { Pending, Active, Completed }
    Status public currentStatus = Status.Pending;

    // ── Struct ──
    struct Person {
        string name;
        uint256 age;
    }
    Person public alice = Person("Alice", 30);
}

Prefixing a state variable with public automatically generates a getter function. Other contracts can read it, but it doesn't create a transaction — reads are free.

02

Functions & Modifiers

Functions are the executable units of a smart contract. They can read state, write state, receive Ether, and enforce access control through modifiers — reusable guard clauses.

Function Visibility & Mutability

  • public — callable internally and externally
  • external — callable only from outside the contract (cheaper for large data)
  • internal — callable only from this contract and derived contracts
  • private — callable only from this contract
  • view — reads state but does not modify it (no gas for external calls)
  • pure — neither reads nor modifies state
  • payable — can receive Ether
Solidity 
contract Functions {
    uint256 public value;

    // ── Modifier ──
    address public owner;
    modifier onlyOwner() {
        require(msg.sender == owner, "Not owner");
        _;
    }

    constructor() {
        owner = msg.sender;
    }

    function setValue(uint256 _newValue) public onlyOwner {
        value = _newValue;
    }

    function getValue() public view returns (uint256) {
        return value;
    }

    function multiply(uint256 a, uint256 b) public pure returns (uint256) {
        return a * b;
    }

    function deposit() public payable {
        // msg.value contains the Ether sent
    }
}

How Modifiers Work

A modifier is a wrapper around a function. The _; symbol marks where the function body is injected. If the modifier's code require or revert fails, the function never executes — saving gas.

Practice: Functions & Modifiers
  1. Create a uint256 public count variable
  2. Write a increment() public function that adds 1 to count
  3. Write a decrement() public function that subtracts 1, but reverts if count is 0
  4. Add an onlyOwner modifier to both functions
Solidity 
contract Counter {
    address public owner;
    uint256 public count;

    modifier onlyOwner() {
        require(msg.sender == owner, "Not owner");
        _;
    }

    constructor() { owner = msg.sender; }

    function increment() public onlyOwner { count += 1; }

    function decrement() public onlyOwner {
        require(count > 0, "Count is zero");
        count -= 1;
    }
}

Inheritance & Contracts

Solidity supports multiple inheritance — a contract can inherit from several parent contracts using the is keyword. This enables code reuse, modular design, and the popular "mix-in" pattern.

Inheritance Rules

  • Use contract B is A to inherit from A
  • Functions marked virtual can be overridden in child contracts
  • Overriding functions must use the override keyword
  • Multiple inheritance: contract C is A, B
  • abstract contracts have unimplemented functions and cannot be deployed
  • interface contracts declare function signatures without implementation
Solidity 
contract Ownable {
    address public owner;
    event OwnershipTransferred(...);

    constructor() { owner = msg.sender; }

    modifier onlyOwner() {
        require(msg.sender == owner, "Not owner");
        _;
    }

    function transferOwnership(address _newOwner)
        public virtual onlyOwner { ... }
}

contract MyToken is Ownable {
    function mint(uint256 _amount) public onlyOwner {
        totalSupply += _amount;
    }

    function transferOwnership(address _newOwner)
        public override onlyOwner { ... }
}

Composition over inheritance is common in Solidity. Many projects import reusable modules (libraries) rather than deep inheritance trees. Use inheritance when contracts share a genuine is-a relationship.

Interfaces vs Abstract Contracts

  • Interface: Pure function signatures, no state, no constructor — for maximum interoperability (e.g., ERC-20, ERC-721)
  • Abstract: Can have state and implemented functions, but at least one function is unimplemented — useful for base contracts that define a skeleton

Events & Logging

Events are Solidity's primary mechanism for communicating with off-chain consumers (dApps, indexers, explorers). When emitted, events are stored in the transaction receipt logs — they don't cost storage gas, making them much cheaper than state variables for emitting data.

Event Essentials

  • Declared with event keyword at the contract level
  • Emitted with emit inside functions
  • Parameters marked indexed (max 3) become searchable by off-chain tools
  • Indexed parameters are also called topics
  • Non-indexed parameters are stored as data (cheaper to emit)
Solidity 
contract EventDemo {
    // ── Event Declarations ──
    event Transfer(address indexed from,
                   address indexed to,
                   uint256 amount);
    event Approval(address indexed owner,
                   address indexed spender,
                   uint256 amount);
    event Log(string message, uint256 timestamp);

    function send(address _to, uint256 _amount) public {
        emit Transfer(msg.sender, _to, _amount);
    }
}
Parameter Type Keyword Gas Cost Searchable
Indexed (topic)indexed~375 gasYes — by event log filters
Non-indexed (data)(none)~8 gas per byteNo — must decode ABI

Events are not accessible from within the blockchain — other contracts cannot read events. Their purpose is off-chain consumption: wallets, block explorers (Etherscan), and indexers (The Graph) watch for events to update their UI.

Error Handling — require, revert & assert

Smart contracts must handle invalid inputs, unauthorized access, and logic violations gracefully. Solidity provides three ways to revert a transaction (undo all state changes and refund unused gas).

The Three Tools

  • require(condition, "message") — Use for input validation, access control, and external call checks. Refunds remaining gas. Most commonly used.
  • revert("message") — Use in complex if/else flows. Functional equivalent of require(false, msg).
  • assert(condition) — Use to check for invariants that should never be false. Consumes all remaining gas. Reserved for critical internal bugs.
Solidity 
contract ErrorHandling {
    address public owner;

    // ── require: input validation ──
    function withdraw(uint256 _amount) public {
        require(_amount > 0, "Amount must be greater than zero");
        require(address(this).balance >= _amount, "Insufficient balance");
        payable(msg.sender).transfer(_amount);
    }

    // ── revert: conditional flow ──
    function adminAction(bool _authorized) public {
        if (!_authorized) {
            revert("Not authorized");
        }
    }

    // ── assert: internal invariant ──
    function checkInvariant() public view {
        assert(address(this).balance >= totalDeposits);
    }
}
Function Gas Refund When to Use
require()Remaining gas refundedInput validation, access control, external call checks
revert()Remaining gas refundedComplex conditional flows, custom error logic
assert()All gas consumedInvariant violations, should-never-happen bugs

Gas warning: assert() consumes all remaining gas when it fails. Since Solidity 0.8.0, the compiler automatically inserts assert checks for arithmetic overflow/underflow, so manual assert() is rarely needed.

Basic Smart Contract Walkthrough

Let's bring everything together with a complete, deployable smart contract: a Simple Vault that lets users deposit and withdraw ETH, with an owner who can pause the contract in emergencies.

Simple Vault — Full Contract

This contract combines state variables, events, modifiers, error handling, and a practical use case. Read through each part carefully.

Solidity 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract SimpleVault {
    // ── State ──
    address public owner;
    bool public paused;
    mapping(address => uint256) public balances;

    // ── Events ──
    event Deposited(address indexed user, uint256 amount);
    event Withdrawn(address indexed user, uint256 amount);
    event Paused(address indexed by);
    event Unpaused(address indexed by);

    // ── Modifiers ──
    modifier onlyOwner() {
        require(msg.sender == owner, "Not owner"); _;
    }

    modifier whenNotPaused() {
        require(!paused, "Paused"); _;
    }

    constructor() { owner = msg.sender; }

    function deposit() public payable whenNotPaused {
        require(msg.value > 0, "Must send ETH");
        balances[msg.sender] += msg.value;
        emit Deposited(msg.sender, msg.value);
    }

    function withdraw(uint256 _amount) public whenNotPaused {
        require(_amount > 0, "Amount must be > 0");
        require(balances[msg.sender] >= _amount, "Insufficient balance");
        balances[msg.sender] -= _amount;
        payable(msg.sender).transfer(_amount);
        emit Withdrawn(msg.sender, _amount);
    }

    function togglePause() public onlyOwner {
        paused = !paused;
    }

    function getContractBalance() public view
        returns (uint256) {
        return address(this).balance;
    }
}

Key Takeaways

  • Modifiers (onlyOwner, whenNotPaused) keep access control declarative and reusable
  • Events enable off-chain apps to track deposits and withdrawals
  • require() guards every function against invalid input
  • mapping provides gas-efficient per-user storage
  • payable allows the contract to receive ETH
  • The constructor runs once at deployment, setting the initial owner
